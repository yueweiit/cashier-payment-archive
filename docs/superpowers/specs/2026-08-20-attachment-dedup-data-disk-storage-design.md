# 附件去重与应用服务器数据盘迁移设计

## 1. 背景与目标

当前应用服务器包含约 100GB 系统盘和约 500GB 数据盘。应用程序、SQLite 主库及附件目前主要位于系统盘，其中附件引用数量明显高于真实钉钉源文件数量，且批次快照会复制附件文件，导致空间重复占用。

本次改造的目标是：

- 修复钉钉附件重复识别，避免同一附件被反复下载和登记。
- 在保留业务关联的前提下，让相同文件内容只保存一份物理副本。
- 将附件从应用服务器系统盘迁移至约 500GB 数据盘。
- 新上传及新同步的附件直接写入数据盘。
- 迁移后保留系统盘旧文件 30 天，支持快速回滚。
- 停止在批次快照中复制附件实体，避免容量随快照成倍增长。

数据库服务器约 1TB 数据盘继续仅用于 PostgreSQL 数据、备份及恢复空间，不参与附件存储。本期不接入 OSS，也不迁移 SQLite 主库。

## 2. 范围与非目标

### 2.1 本期范围

- 普通请款附件。
- 付款凭证附件。
- 钉钉流程及中间表同步得到的附件。
- 物理文件去重、路径迁移、兼容读取、清理与回滚。
- 快照中的附件保存方式调整。

### 2.2 非目标

- 不迁移到阿里云 OSS。
- 不把 SQLite 主库迁移到数据盘或 PostgreSQL。
- 不改变附件、付款凭证在界面上的业务归属和权限。
- 不自动删除跨请款或跨批次的业务附件关系。
- 不在首次迁移时永久删除任何旧文件。

## 3. 核心业务规则

### 3.1 业务关系与物理文件分离

附件关系描述“哪个附件属于哪条请款或付款”，物理文件对象描述“文件内容实际存在哪里”。多个附件关系可以引用同一个物理文件对象。

### 3.2 去重边界

- 同一请款中的同一个钉钉真实 `fileId` 只保留一条附件关系。
- 跨请款、跨批次继续保留各自的业务附件关系。
- 相同 SHA-256 的文件只保存一份物理副本。
- 文件内容相同但业务名称不同的附件，保留各自名称和关系，仅共用物理文件。
- 无真实 `fileId` 的人工上传附件只自动合并物理文件，不会仅凭哈希删除业务附件条目。
- 删除一个附件关系时，只有物理文件已经没有任何引用且超过隔离期，才允许删除物理文件。

## 4. 存储架构

### 4.1 路径规划

新增独立附件存储配置，避免改变现有 SQLite 数据库路径：

- SQLite 及应用元数据：继续使用现有 `PAYMENT_APP_DATA_DIR`。
- 附件存储根目录：新增 `PAYMENT_ATTACHMENT_STORAGE_DIR`。
- 线上目标值：`/data/cashier-payment/storage`。
- 临时下载目录：`/data/cashier-payment/storage/tmp`。
- 内容寻址目录：`/data/cashier-payment/storage/attachments/sha256`。
- 迁移隔离目录：`/data/cashier-payment/quarantine` 或迁移清单指定的系统盘旧目录。

物理文件采用不可变的内容寻址路径：

```text
attachments/sha256/<哈希前两位>/<完整 SHA-256>
```

原始文件名、扩展名、MIME 类型和来源信息保存在数据库，不依赖磁盘文件名表达业务含义。

### 4.2 物理文件对象

新增物理文件对象表，例如 `file_objects`，主要字段为：

- `id`
- `sha256`，唯一
- `size_bytes`
- `mime_type`
- `storage_backend`，本期固定为 `local`
- `storage_path`
- `status`：`pending`、`ready`、`quarantined`、`missing`
- `created_at`
- `verified_at`

现有普通附件和付款凭证表增加 `file_object_id`，继续保存显示名称、业务类型、来源和创建信息。过渡期保留原 `file_path`，用于兼容读取和回滚。

### 4.3 稳定来源标识

钉钉附件使用真实钉钉 `fileId`，不能使用中间表中可能重新生成的附件行 ID。来源身份至少包含：

- 来源系统；
- 流程实例或来源业务记录标识；
- 真实 `fileId`。

同一请款的逻辑唯一约束为：

```text
(request_id, source_system, source_instance_id, source_file_id)
```

历史中间表行 ID可保留在来源元数据中用于排查，但不再作为去重主键。

## 5. 新附件写入流程

1. 读取外部附件元数据。
2. 使用稳定来源标识检查该请款是否已经存在附件关系；已存在则跳过下载。
3. 对未知附件使用受限并发下载，默认同时 3～5 个，写入数据盘临时目录。
4. 下载过程中流式计算 SHA-256，并校验文件大小和允许的文件类型。
5. 如果 SHA-256 已存在，删除临时文件并复用现有物理文件对象。
6. 如果不存在，通过同一文件系统内的原子重命名写入内容寻址目录，再将物理对象标记为 `ready`。
7. 最后创建业务附件关系。物理文件未校验成功时不得创建可用附件关系。

人工上传和付款凭证沿用相同的物理文件写入流程，但保持现有业务表和界面入口不变。

钉钉状态及评论同步与附件下载解耦：单个附件失败不能让流程状态和评论同步整体失败；失败附件记录原因并允许重试。

## 6. 历史迁移流程

### 6.1 盘点阶段

- 扫描数据库附件记录和磁盘文件。
- 记录原路径、文件大小、SHA-256、业务引用、钉钉来源标识和异常状态。
- 输出唯一文件、重复文件、缺失文件、无引用文件和来源冲突清单。
- 此阶段只读，不修改数据库或删除文件。

### 6.2 回滚点

- 使用 SQLite Backup API 生成一致性数据库备份。
- 保存迁移清单、文件数量、总容量和清单文件的 SHA-256。
- 记录服务版本、配置和附件根目录。
- 数据库备份及迁移清单不得与待清理文件位于同一目录。

### 6.3 文件复制与校验

- 根据 SHA-256 将每个唯一文件复制到数据盘内容寻址目录。
- 复制完成后重新计算目标文件哈希和大小。
- 校验失败的文件不进入切换阶段，并在报告中标记。
- 迁移脚本必须幂等，中断后可以从已有校验结果继续。

### 6.4 数据库关联

- 分批建立物理文件对象并为附件关系写入 `file_object_id`。
- 每批使用短事务，失败时只回滚当前批次。
- 已迁移关系优先读取数据盘；没有 `file_object_id` 或新文件不可用时回退原路径。
- 文件复制和校验在事务外完成，事务只负责最终关联更新。

### 6.5 切换新写入

- 验证已迁移文件后，将线上 `PAYMENT_ATTACHMENT_STORAGE_DIR` 指向数据盘。
- 新上传、新付款凭证和新钉钉附件只写数据盘。
- 切换期间保留旧路径读取能力。

### 6.6 旧文件隔离与清理

- 数据盘读取稳定后，将已确认迁移的系统盘旧物理文件标记为隔离，保留 30 天。
- 30 天内不永久删除旧文件，不重复计入有效附件。
- 到期清理前再次检查目标文件哈希、数据库引用和最近访问异常。
- 只有目标文件可用、旧文件不再被读取且清单校验通过时，才允许永久删除。

## 7. 历史重复附件清理

- 同一请款、相同真实钉钉 `fileId` 的重复关系选择一条规范记录保留。
- 规范记录优先选择来源信息完整、创建时间较早、文件可用且已有关联展示信息的记录。
- 其他重复关系不立即硬删除，先写入清理审计并进入可恢复状态。
- 相同内容但不同 `fileId` 的关系不自动删除，仅共享物理文件。
- 跨请款和跨批次关系永不因为内容相同而删除。
- 历史来源无法确认真实 `fileId` 时，以保留业务关系为优先，只做物理文件去重。

## 8. 快照调整

批次快照继续保存请款、付款、附件关系及恢复所需元数据，但不再复制物理附件文件。恢复快照时重新关联现有物理文件对象。

如果恢复时物理文件缺失，恢复流程应报告附件异常，不得生成指向不存在文件的正常附件记录。物理文件对象的引用计数或引用查询必须覆盖当前数据和仍在保留期内的快照关系。

## 9. 错误处理与一致性

- 写文件采用“临时文件 → 校验 → 原子重命名”。
- 文件哈希不一致时保留旧文件，不更新数据库关联。
- 数据库更新失败时回滚当前批次，物理文件作为待清理孤儿对象记录。
- 文件不存在或损坏时显示明确的“附件异常”，保留原路径和来源信息。
- 物理文件删除前实时检查普通附件、付款凭证和快照引用。
- 清理、迁移和同步操作使用任务状态及审计日志，支持失败重试和断点续跑。
- 重复执行迁移或同步不得再次生成物理文件或附件关系。

## 10. 权限与安全

- 下载和预览继续通过现有登录及请款权限校验，不能直接暴露任意磁盘路径。
- 存储根目录仅允许应用服务账号和运维人员访问。
- 上传文件名不得参与最终磁盘路径，避免路径穿越。
- 继续执行文件大小和类型限制；服务端根据文件内容辅助确认 MIME 类型。
- 迁移报告和日志不得记录数据库密码、登录令牌或外部附件临时下载凭证。

## 11. 监控与运维

至少记录以下指标：

- 业务附件关系总数；
- 唯一物理文件数量及总容量；
- 去重节省容量和去重比例；
- `pending`、`missing`、孤儿和隔离文件数量；
- 附件同步下载成功率、失败率和耗时；
- 系统盘和数据盘使用率；
- 仍在通过旧路径读取的次数。

数据盘使用率达到 80%时告警，达到 85%时严重告警。系统盘应继续保留现有容量告警，并重点监测迁移后是否仍有附件写入旧目录。

## 12. 测试与验收

### 12.1 功能测试

- 同一钉钉附件即使中间表行 ID变化，也不会产生新关系或重复下载。
- 相同内容、不同文件名可以共享物理文件，同时保留各自名称。
- 跨请款、跨批次关系保持完整。
- 删除一条关系不会删除其他关系仍引用的文件。
- 普通附件、付款凭证、钉钉附件均可上传、预览、下载和删除。
- 同步失败后可以重试，且不会产生重复数据。

### 12.2 迁移测试

- 迁移前后业务附件关系数量一致，只有已确认的同请款同 `fileId` 重复关系被规范化。
- 数据盘文件大小和 SHA-256 与源文件一致。
- 迁移期间新旧路径均可读取。
- 服务重启后新附件只写入数据盘。
- 迁移脚本中断后可以继续，不重复复制和写入。
- 30 天内能够恢复数据库备份或切回旧路径。

### 12.3 容量验收

- 系统盘附件占用显著下降。
- 相同附件不再因周结转或快照产生新的物理副本。
- 数据盘统计容量与唯一物理文件容量基本一致，差异仅来自临时文件、迁移清单和隔离区。

## 13. 发布顺序

1. 部署数据模型和双路径读取能力，暂不切换写入。
2. 运行只读盘点并审核重复、缺失和冲突报告。
3. 生成一致性数据库备份及迁移清单。
4. 将唯一文件复制到数据盘并完成哈希校验。
5. 分批关联物理文件对象，验证预览和下载。
6. 切换新附件写入目录到数据盘。
7. 修改快照逻辑，停止复制附件实体。
8. 将旧文件保留 30 天并监控旧路径回退次数。
9. 30 天后根据清理报告人工确认，再永久释放系统盘空间。

## 14. 回滚方案

- 切换后发生异常时，立即停止新的迁移和清理任务。
- 将附件读取和写入配置切回原目录。
- 如果只有个别关联异常，回滚对应迁移批次；如果关联普遍异常，恢复迁移前 SQLite 一致性备份。
- 系统盘旧文件在 30 天内保持不变，因此回滚不依赖重新下载外部附件。
- 回滚完成后重新核对附件关系数量、随机文件哈希和下载功能。
