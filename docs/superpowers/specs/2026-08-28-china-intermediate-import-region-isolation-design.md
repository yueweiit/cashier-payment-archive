# 中国工作台中间表拉取地区隔离设计

## 背景与根因

“从钉钉支出中间表拉取”属于中国请款工作台入口，但共用的外部支出映射能力同时服务中国与墨西哥流程。历史改动 `369077a` 将标准支出查询的执行地区条件从仅中国放宽为“中国或墨西哥”，随后墨西哥审批跟踪功能又继续复用了同一套映射逻辑。

因此目前存在两层缺口：

- 预览查询会直接返回执行地区为墨西哥的运营、采购支出；月结付款查询没有地区条件，映射后也未再过滤。
- 实际导入接口会重新按来源主键取数，但没有复核地区；即使前端隐藏记录，仍可能通过直接请求把墨西哥记录导入中国工作台。

本次只收紧中国工作台的预览和导入边界，不改变共用映射器及墨西哥审批发现、跟踪能力。

## 确认方案

采用“查询过滤 + 映射后统一判定 + 导入防线”的方案。

### 地区判定

继续复用现有 `resolve_region` 规则：

1. 钉钉流程中的明确执行地区优先，`墨西哥/México/Mexico` 判定为墨西哥，`中国/China` 判定为中国。
2. 执行地区为空时，使用现有来源 Sheet 映射辅助判断。
3. 明确为墨西哥，或执行地区为空但来源 Sheet 明确属于墨西哥的记录，不允许进入中国工作台。
4. 执行地区为空且来源 Sheet 未配置的历史记录暂时保留，避免本次修复意外屏蔽旧的中国记录；此类数据仍沿用现有字段校验和人工核对流程。

货币不作为地区判定依据，避免 USD 等跨地区币种造成误判。

### 预览查询

- 运营支出、采购支出在 PostgreSQL 查询阶段只保留明确中国或执行地区为空的记录，尽早排除明确墨西哥数据。
- 所有来源映射完成后使用统一的中国工作台判定函数再次过滤，覆盖月结付款、空地区加墨西哥 Sheet、以及来源数据格式差异。
- 申请人筛选选项使用相同地区规则，确保墨西哥审批人不会出现在中国工作台筛选列表中，数量与可见记录保持一致。
- 精确输入钉钉单号时也不绕过地区隔离。

### 实际导入

- 导入接口按来源主键重新读取记录后，再调用同一地区判定函数。
- 墨西哥记录加入明确错误：`执行地区为墨西哥，不允许导入中国请款工作台`。
- 批量导入继续采用现有部分成功语义：合规中国记录可正常导入，墨西哥记录计入无效记录并跳过，不让单条错误破坏整批合法数据。
- 不信任前端传入的地区信息，始终以后端重新读取的钉钉源数据为准。

## 兼容性与边界

- `map_external_expense` 与 `map_monthly_payment` 继续支持中国和墨西哥，避免破坏墨西哥审批同步、金额与币种解析。
- 墨西哥审批跟踪的全量发现、地区解析、权限与统计逻辑保持不变。
- 已经导入的历史请款不删除、不改写；现有中国工作台列表和每日应付继续使用已建立的地区隔离规则。
- 不增加数据库字段或迁移，不修改前端接口格式。

## 测试与验收

自动化测试覆盖：

- 标准支出 SQL 不再允许明确墨西哥地区，同时继续保留中国和空地区兼容规则。
- 运营、采购及月结预览均排除明确墨西哥记录。
- 执行地区为空但来源 Sheet 属于墨西哥时排除；空地区且未知 Sheet 的旧记录继续保留。
- 申请人筛选项不包含仅出现在墨西哥记录中的人员。
- 直接构造导入请求时，后端仍跳过墨西哥记录并返回明确错误。
- 中国记录可正常预览和导入；共用映射器仍能正确解析墨西哥记录，墨西哥审批发现测试不回退。
- 运行相关后端测试、全量后端测试、前端测试和生产构建。
