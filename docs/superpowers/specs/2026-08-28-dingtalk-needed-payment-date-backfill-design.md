# 钉钉同步回填需求付款日期设计

## 背景与根因

每日应付按“需求付款日期不晚于统计日”纳入当日到期和日终待付。没有需求付款日期的请款无法归属到任何统计日，因此会被每日应付跳过。

生产单号 `202607221050000501984` 在系统中的需求付款日期一直为空，但钉钉支出中间表当前能正确解析出 `2026-07-24`。现有“同步钉钉流程”会刷新审批元数据、收款人、总经理审批、地区、付款候选与附件，但不会回填需求付款日期。同步最后写入的 `dingtalk.sync` 历史事件因此仍保存空日期，造成该待付项持续缺席。

## 目标

当钉钉中间表有有效需求付款日期、而系统当前请款日期为空时，由现有钉钉同步自动回填。回填后立即通过既有每日应付历史事件生效。

## 非目标

- 不覆盖系统中已有的人工日期，即使它与钉钉不同。
- 不改变每日应付的到期口径；未来日期仍要等到对应统计日才出现。
- 不在应用启动时全库扫描，不增加启动期对中间表的依赖。
- 不引入数据库字段或迁移。

## 方案

### 1. 元数据边界

`fetch_external_expense_metadata()` 继续批量查询运营支出、采购支出和月结付款三类来源。在现有标准化映射完成后，每个唯一来源的元数据额外携带顶层 `needed_payment_date`，值取自已有映射结果：

- 运营支出：中间表 `payment_date`。
- 采购支出：钉钉表单组件“付款日期”。
- 月结付款：表单明细中可解析的最早付款日期。

元数据冲突或未匹配时不回填，保持现有冲突处理规则。

### 2. 只补空值的同步规则

钉钉同步处理每条请款时计算：

1. 先保留 `payment_requests.needed_payment_date` 当前值。
2. 仅当当前值去空格后为空，且唯一匹配的元数据提供有效 ISO 日期时，才写入该日期。
3. 如果当前值非空，则不比较、不警告、不覆盖。
4. 如果来源日期为空或无效，则保持空值。

日期更新与当前同步的其他字段使用同一个数据库事务，不增加中间状态。

### 3. 每日应付历史

现有同步在更新请款、重算付款汇总和地区后，会调用 `record_request_state(..., event_type="dingtalk.sync")`。日期回填必须发生在该调用之前，使新历史版本携带回填日期。

重复同步应幂等：第一次回填后，后续同步看到系统日期已非空，不再修改它。现有同步历史事件仍可记录其他状态变化。

## 错误处理

- 中间表查询失败时，整个同步仍按现有规则失败并回滚，不写入部分日期。
- 同一钉钉单号对应多个来源时，不选择其中一个日期，仍标记冲突。
- 回填不引入新的业务警告或用户交互，避免改变已有同步操作方式。

## 测试设计

后端回归测试必须先证明旧实现失败，然后覆盖：

1. 元数据包含映射后的 `needed_payment_date`。
2. 系统日期为空时，同步回填来源日期。
3. 系统已有人工日期时，同步保留人工值。
4. 来源日期为空时，系统仍为空。
5. 回填后的 `dingtalk.sync` 历史事件包含新日期，相应请款在每日应付中出现。
6. 重复同步不覆盖已有日期。

运行相关后端用例、全量后端用例（记录现有无关时间边界用例）、前端用例和生产构建。

## 上线与验收

1. 合并前确认主分支仅保留用户自有的未跟踪目录。
2. 部署前读取运行中服务的真实数据库路径，停服务并使用 `backup_database()` 生成不覆盖的完整备份。
3. 部署已验证提交，等待服务和公网 HTTP 200，检查新日志。
4. 使用已登录的管理/财务会话对当前草稿批次执行一次“同步钉钉流程”。
5. 验收单号 `202607221050000501984`：系统需求付款日期为 `2026-07-24`，已付 `14,500`，待付 `14,500`，中国地区已核定，并出现在 `2026-08-28` 每日应付明细中。
6. 确认其他已有人工需求付款日期未被改写。
